# Rugby History Book — Implementation Plan

## Project Context

We currently have a static rugby team website hosted on Cloudflare.

We want to add a private "History Book" feature to the website.

The History Book should:

* Be accessible from the existing website under `/history`
* Be protected by a shared team password (for browsing/submitting memories)
* Allow users to submit memories from the website
* Allow users to submit memories from Discord
* Allow each memory to contain:

  * year
  * optional date
  * optional title
  * caption
  * one or more photos
  * submission source
  * submitter identity when available
  * created timestamp
* Make submitted memories immediately visible
* Not require admin approval or moderation
* Store metadata in Cloudflare D1
* Store photos in Cloudflare R2
* Serve photos via **public R2 URLs** (CDN-backed) for performance and lower Worker usage
* Accept that photo object URLs are readable without a History Book session if someone has the link

The existing public website should remain mostly static.

### Privacy posture (explicit tradeoff)

* `/history` pages and history APIs are password-protected.
* Photo **files** are public at the object URL level (anyone with the URL can view them).
* Mitigate casual discovery by using unguessable object keys (UUIDs), not sequential filenames.
* Do **not** proxy image bytes through the Worker on every page view.

# Target Architecture

```text
                     Club Member
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
      Static Rugby Site            Discord
       /history/submit            /yearbook
             │                       │
             └──────────┬────────────┘
                        ▼
               Cloudflare Worker
                 ┌──────┴──────┐
                 ▼             ▼
                D1            R2
             metadata     upload photos
                              │
                              ▼
                     Public R2 URL / CDN
                              │
                              ▼
                     <img src="https://…">
```

Cloudflare Worker responsibilities:

* authentication
* history API
* memory creation
* photo **upload** to R2 (via binding)
* building/returning public photo URLs in API responses
* Discord interactions
* request validation

Cloudflare D1 responsibilities:

* memories
* photo metadata
* storage IDs (R2 object keys)
* submission metadata

Cloudflare R2 responsibilities:

* original image object storage
* public HTTP access for stored objects (custom domain preferred)

---

# Core Domain Model

Use a `Memory` as the main domain object.

Conceptually:

```text
Memory
├── id
├── year
├── event_date
├── title
├── caption
├── source
├── submitted_by
├── created_at
└── photos[]
```

Do not model the application around R2 key prefixes or “folders.”

R2 should only be a storage implementation.

# Step 1 — Create the D1 Database

Create a Cloudflare D1 database for the History Book.

Suggested name:

```text
rugby-history
```

(Actual deployed name may differ, e.g. `south-pitt-history-metadata`.)

Create a `memories` table.

Example schema:

```sql
CREATE TABLE memories (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    year INTEGER NOT NULL,
    event_date TEXT,
    title TEXT,
    caption TEXT NOT NULL,
    source TEXT NOT NULL,
    submitted_by TEXT,
    created_at TEXT NOT NULL
);
```

Create a `memory_photos` table.

Example schema:

```sql
CREATE TABLE memory_photos (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    memory_id INTEGER NOT NULL,
    storage_provider TEXT NOT NULL,
    storage_id TEXT NOT NULL,
    original_filename TEXT,
    sort_order INTEGER NOT NULL DEFAULT 0,

    FOREIGN KEY(memory_id)
        REFERENCES memories(id)
);
```

Use generic storage fields:

```text
storage_provider
storage_id
```

Do not hardcode the schema around R2-specific field names.

Example:

```text
storage_provider = "r2"
storage_id = "memories/42/a1b2c3d4-team-photo.jpg"
```

Public URLs are derived at read time from a configured public base URL + `storage_id` (preferred). Do not require storing full public URLs in D1 unless needed for legacy imports.

Initial API routes:


# Step 7 — Create the Cloudflare R2 Bucket (Public Read)

Create an R2 bucket for History Book photos.

Suggested name:

```text
south-pitt-rfc-photos
```

Configure the Worker with an R2 binding in Wrangler, for example:

```jsonc
"r2_buckets": [
  {
    "binding": "HISTORY_PHOTOS",
    "bucket_name": "south-pitt-rfc-photos"
  }
]
```

Enable **public read** access for objects, preferably via a **custom domain** on the club site, e.g.:

```text
https://history-photos.southpittrugby.com/<object-key>
```

Store the public base URL as a Worker var/secret, e.g.:

```text
R2_PUBLIC_BASE_URL=https://history-photos.southpittrugby.com
```

The Worker binding remains the write path (`put` / `delete`). Browsers read objects directly from the public base URL.

Object keys should be unguessable. Example:

```text
memories/<memory-id>/<uuid>-<safe-filename>
```

The application must not require browsing R2 “folders” to function.

Manual Cloudflare setup (once):

1. Create the R2 bucket.
2. Attach a public custom domain (preferred) or enable the managed public bucket URL.
3. Add the Wrangler R2 binding.
4. Set `R2_PUBLIC_BASE_URL` for local (`.dev.vars`) and production.

# Step 8 — Create a Photo Storage Abstraction

Do not let the rest of the application directly depend on R2 APIs.

Create an interface conceptually similar to:

```typescript
interface PhotoStorage {
    upload(file: File, metadata?: object): Promise<StoredPhoto>;
    delete(id: string): Promise<void>;
    publicUrl(id: string): string;
}
```

Example returned value:

```typescript
{
    provider: "r2",
    id: "memories/42/a1b2c3d4-team-photo.jpg"
}
```

Implement:

```text
R2PhotoStorage
```

* `upload` / `delete` use `env.HISTORY_PHOTOS`
* `publicUrl` returns `${R2_PUBLIC_BASE_URL}/${storage_id}`

The memory service should depend on the generic `PhotoStorage` abstraction.

A Worker `download()` / photo-proxy endpoint is **not** required for normal viewing.

# Step 10 — Store Photo Metadata in D1

When an image is uploaded successfully to R2, create a `memory_photos` record.

Example:

```text
memory_id = 42
storage_provider = "r2"
storage_id = "memories/42/a1b2c3d4-team-photo.jpg"
original_filename = "team-photo.jpg"
sort_order = 0
```

If multiple images exist, each should have its own `memory_photos` row.

API responses should include a computed `url` for each photo using `R2_PUBLIC_BASE_URL`.

# Step 11 — Use Public R2 URLs in the Frontend

Do not proxy image bytes through the Worker for normal History Book viewing.

HTML should use URLs similar to:

```text
https://history-photos.southpittrugby.com/memories/42/a1b2c3d4-team-photo.jpg
```

rather than:

```text
/api/history/photos/123
```

Checklist for this step:

* API memory model includes public `photos[].url`
* `/history` renders `<img src={photo.url}>`
* Confirm CDN/cache headers are acceptable
* Confirm object keys are not trivially guessable

Optional later: signed/short-lived URLs if privacy requirements tighten. Not part of MVP.

# Step 12 — Add Shared Password Authentication

Create:

```text
/history/login
```

The page should ask for one shared team password.

Example:

```text
Hooligans History Book

Team password
[ **************** ]

[ Enter ]
```

Implement:

```text
POST /api/history/login
```

The Worker should validate the submitted password against a securely stored secret or password hash.

On successful authentication, set a signed session cookie.

Cookie requirements:

```text
HttpOnly
Secure
SameSite=Lax
```

Use a reasonably long expiration because this is a low-risk private club archive.

Protect:

```text
/history
/history/*
/api/history/*
```

except for the login endpoint.

Do not store the team password in frontend JavaScript.

Note: password protection covers pages/APIs. Public R2 photo URLs remain directly fetchable.

# Step 21 — Handle Partial Failures

Define expected behavior if:

```text

but R2 upload fails
```

or:

```text

```

Avoid leaving orphaned data where practical.

The memory creation service should coordinate storage and metadata creation.

Document the chosen failure strategy.

# Important Architectural Rules

When implementing this project, preserve these rules:

1. The existing public website should remain mostly static.

2. D1 stores structured metadata.

3. Cloudflare R2 stores image files.

4. D1 stores R2 object keys (`storage_id`). Public URLs are derived from `R2_PUBLIC_BASE_URL` + key.

5. R2 objects are publicly readable at their object URLs (by design, for performance).

6. Browsers load photos directly from public R2/CDN URLs. Do not proxy every image through the Worker.

7. Website submissions and Discord submissions use the same `createMemory()` business logic.

8. Discord is an input interface, not a storage system.

9. R2 is a storage implementation, not the application's database.

10. Do not build admin approval or moderation functionality.

11. Successful submissions become immediately visible.

12. Keep infrastructure-specific code behind abstractions where practical.

13. Keep secrets in Cloudflare secrets; use Worker R2 bindings for uploads.

14. Do not expose the shared team password to frontend JavaScript.

15. Optimize for a simple MVP before adding tags, people, comments, likes, search, or other history features.
